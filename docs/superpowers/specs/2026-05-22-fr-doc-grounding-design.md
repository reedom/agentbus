# FR doc grounding for agentbus — design

- Date: 2026-05-22
- Status: approved (brainstorm complete; implementation plan TBD)
- Repository: `github.com/reedom/agentbus`

## 1. Goal

Establish AI-grounded documentation for agentbus so future development has a
durable, machine-traceable source of truth. Functional Requirement (FR)
documents under `docs/fr/` describe each product feature; a `kusara`
cross-reference graph keeps them linked to reference docs and code modules; a
Claude Code hook surfaces drift as edits happen.

The existing brainstorm artifacts under `docs/superpowers/` (the original
mcp-bus design spec and implementation plan) are a one-time extraction source.
Once FR docs exist, `docs/superpowers/` is deleted entirely — git history
retains it.

### 1.1 Reference patterns

- `reedom/roki` — FR docs under `docs/fr/` with `refs:` YAML frontmatter, a
  `docs/kinds.md` kusara manifest, and a `PostToolUse` hook (`refs-postedit.sh`)
  that runs `kusara validate` / `touched` after edits.
- `reedom/kusara` — the markdown cross-reference graph CLI and its Claude
  plugin (`/kusara:setup`, `/kusara:sync`, `/kusara:check`, `/kusara:add-ref`;
  skills `refs-schema`, `kinds-manifest`; agent `doc-maintainer`).
- `audiflow/audiflow-ecosystem` — doc content style: each doc carries Purpose,
  Definitions, Responsibilities / Non-responsibilities, Read-next, and an
  explicit "When to update" trigger section.

### 1.2 Non-goals

- Numbered per-requirement IDs (`req:...`). FRs are tracked at whole-FR
  granularity; individual requirements live as prose inside each FR.
- A permanent `spec` doc kind. The superpowers spec is extracted then retired.
- Copying kusara's plugin skills/agent into agentbus — they are consumed from
  the installed kusara plugin.

## 2. Doc kinds

Two kusara kinds:

| Kind | Location | ID pattern | Purpose |
|---|---|---|---|
| `fr` | `docs/fr/[0-9]*.md` | `fr:{slug}` | functional requirement per product feature |
| `reference` | `docs/reference/[a-z]*.md` | `ref:{slug}` | protocol + integration reference docs |

Graph flow: `fr` → `reference` → code modules. FRs link to reference docs via
`related`, and to code via `modules`.

## 3. Final docs/ layout

```
docs/
├─ README.md                  # overview (untracked by kusara)
├─ kinds.md                   # kusara manifest
├─ fr/
│  ├─ README.md               # how FRs work here + design guidance
│  ├─ _template.md            # skeleton for new FR
│  ├─ index.md                # generated by `kusara index`
│  └─ NN-*.md                 # FR docs
└─ reference/
   ├─ index.md                # generated by `kusara index`
   ├─ protocol.md             # moved from docs/protocol.md
   ├─ slack-bridge.md         # moved from docs/examples/slack-bridge.md
   └─ extbot-integration.md   # moved from docs/examples/extbot-integration.md
```

`docs/protocol.md` and `docs/examples/*.md` move into `docs/reference/` so each
kind's `index.output` is coherent. `docs/examples/` is removed.
`docs/superpowers/` is deleted after extraction. `docs/README.md` internal
links are updated: the spec link points at `docs/fr/index.md`; the protocol and
example links point into `docs/reference/`.

## 5. FR doc template

`docs/fr/_template.md`:

```markdown
---
refs:
  id: fr:NN-<slug>
  kind: fr
  title: "<title>"
  related:
    - fr:XX-other
  modules:
    - crates/.../foo.rs
---

# FR NN: <feature name>

> One-line summary.

## Purpose
Why this exists; the operator/caller contract.

## User-visible Behavior
What a caller observes — surfaces, semantics, ordering.

## Capabilities
What the feature guarantees, as bullets.

## Boundaries
Explicit non-responsibilities — prevents AI inference errors.

## Error Handling
The spec §8.x cases owned by this FR.

## Traceability
- Reference docs: ref:protocol
- Related FR: fr:XX-*

## When to update
Concrete triggers that make this doc stale.
```

`reference` docs carry a minimal `refs:` block: `id`, `kind: reference`,
`title`, optional `related` and `modules`. Their body content is unchanged from
the current `protocol.md` / examples — only frontmatter is added.

## 6. kusara manifest — docs/kinds.md

```yaml
kinds:
  - name: fr
    path_globs: ["docs/fr/[0-9]*.md"]
    id_pattern: "fr:{slug}"
    index:
      output: docs/fr/index.md
  - name: reference
    path_globs: ["docs/reference/[a-z]*.md"]
    id_pattern: "ref:{slug}"
    index:
      output: docs/reference/index.md
```

The `[0-9]*` and `[a-z]*` globs exclude `index.md`, `_template.md`, and
`README.md` from being treated as graph nodes.

`KUSARA_DOC_ROOT` defaults to `docs`, so no environment configuration is
needed.

## 7. Claude Code hook + rules

A new `.claude/` directory in agentbus (none exists today):

```
.claude/
├─ settings.json              # PostToolUse(Edit|Write|MultiEdit) -> refs-postedit.sh
├─ hooks/refs-postedit.sh     # ported from roki, paths adapted to agentbus
└─ rules/refs.md              # authoritative refs: schema rule
```

`settings.json` registers a `PostToolUse` hook matching `Edit|Write|MultiEdit`
that runs `.claude/hooks/refs-postedit.sh`.

`refs-postedit.sh` (ported from roki, adapted to agentbus paths):

1. Mechanical checks (always):
   - `.md` edit → `kusara validate`; silent on success, surface errors.
   - `crates/**` edit → `kusara touched <file>`; surfaces which FR owns the
     changed module.
2. Judgment triggers, appended as hook `additionalContext`:
   - New `.md` file without `refs:` frontmatter → prompt to add it, matching a
     `path_globs` entry in `docs/kinds.md`.
   - `crates/**` source change → guidance on which FR to revisit (refactor =
     none; behavior change = the owning `fr:NN-*`).
   - Existing graph-linked `.md` edit → surface immediate links via
     `kusara show`.
3. Footer: points at `.claude/rules/refs.md` and the `kusara:refs-schema` /
   `kusara:kinds-manifest` plugin skills.

`.claude/rules/refs.md` is the authoritative, in-repo description of the
`refs:` frontmatter schema and the `kinds.md` format — adapted from roki's
equivalent so the contract is documented locally even though the runtime
schema knowledge is delivered by the kusara plugin skills.

## 8. kusara plugin wiring

agentbus consumes the kusara Claude plugin rather than vendoring its
components:

- Contributors install the kusara binary via `/kusara:setup` (which runs
  `cargo install kusara`) or directly with `cargo install kusara`.
- Plugin commands `/kusara:sync`, `/kusara:check`, `/kusara:add-ref` and the
  `doc-maintainer` agent are used as-is from the plugin.
- A new root `CLAUDE.md` (agentbus has none) documents the doc workflow:
  the FR system, the kusara commands, and a pointer to `.claude/rules/refs.md`.

## 9. Migration sequence

1. Create `docs/kinds.md`, `docs/fr/` (with `README.md`, `_template.md`),
   and `docs/reference/`.
2. Move `docs/protocol.md` → `docs/reference/protocol.md` and
   `docs/examples/*.md` → `docs/reference/`; remove `docs/examples/`.
   Add `refs:` frontmatter to each reference doc.
3. Write the 11 FR docs, extracting from the superpowers spec.
4. Run the coverage check (every spec §4–§9 section mapped to an FR).
5. `kusara validate` passes; `kusara index` generates both `index.md` files.
6. Add `.claude/` (settings.json, refs-postedit.sh, rules/refs.md) and root
   `CLAUDE.md`.
7. Update `docs/README.md` links.
8. Delete `docs/superpowers/` entirely — specs and plans.

## 10. Testing / validation

- `kusara validate` is clean (no dangling refs, no duplicate IDs, no unknown
  kinds, all `modules` paths exist).
- `kusara index` regenerates `docs/fr/index.md` and `docs/reference/index.md`
  with no diff on a second run.
- The `refs-postedit.sh` hook is exercised manually: edit an FR `.md` (expect
  silent validate), edit a `crates/**` file (expect `kusara touched` output
  naming the owning FR).
- Coverage check: a one-time manual pass confirming every spec §4–§9 section
  is represented in some FR before `docs/superpowers/` is deleted.
