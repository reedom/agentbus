# FR Doc Grounding Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stand up AI-grounded FR documentation for agentbus — `docs/fr/` functional-requirement docs and `docs/reference/` docs tracked by a kusara cross-reference graph, with a Claude Code `PostToolUse` hook for drift detection — then retire `docs/superpowers/`.

**Architecture:** Two kusara doc kinds (`fr`, `reference`) defined in `docs/kinds.md`. Eleven FR docs are extracted from the existing superpowers spec, each carrying `refs:` YAML frontmatter linking to reference docs and code modules. A ported roki-style `refs-postedit.sh` hook runs `kusara validate` / `kusara touched` after edits. Once FR docs cover the whole spec, `docs/superpowers/` is deleted.

**Tech Stack:** kusara (Rust CLI, `cargo install`), the kusara Claude plugin, Markdown + YAML frontmatter, bash hook script, Claude Code `settings.json`.

**Source spec:** `docs/superpowers/specs/2026-05-21-mcp-bus-design.md` (the mcp-bus design — agentbus's former name). Read it before writing FR docs; it is deleted in the final task.

**Design:** `docs/superpowers/specs/2026-05-22-fr-doc-grounding-design.md`.

**Reference repos** (read-only, on local disk):

## Task 4: FR directory scaffold

**Files:**

- Create: `docs/fr/README.md`

- [ ] **Step 1: Write `docs/fr/_template.md`**

```markdown
---
refs:
  id: fr:NN-<slug>
  kind: fr
  title: "<title>"
  related:
    - fr:XX-other
  modules:
    - crates/.../foo.rs
---

# FR NN: <feature name>

> One-line summary.

## Purpose
Why this exists; the operator/caller contract.

## User-visible Behavior
What a caller observes — surfaces, semantics, ordering.

## Capabilities
What the feature guarantees, as bullets.

## Boundaries
Explicit non-responsibilities — prevents AI inference errors.

## Error Handling
The error cases owned by this FR.

## Traceability
- Reference docs: ref:protocol
- Related FR: fr:XX-*

## When to update
Concrete triggers that make this doc stale.
```

- [ ] **Step 2: Write `docs/fr/README.md`**

```markdown
# Functional Requirements

Each `NN-*.md` file is one Functional Requirement (FR) — the design of record
for one agentbus product feature. FRs are tracked by `kusara` as the `fr` doc
kind (see `../kinds.md`).

## Conventions

- Filename: `NN-<slug>.md`, two-digit ordinal.
- Every FR carries `refs:` YAML frontmatter: a unique `id` (`fr:NN-<slug>`),
  `kind: fr`, a `title`, optional `related` links, and `modules` listing the
  source paths this FR is the design of record for.
- Body sections follow `_template.md`: Purpose, User-visible Behavior,
  Capabilities, Boundaries, Error Handling, Traceability, When to update.
- `index.md` is generated by `kusara index` — do not hand-edit it.

## Workflow

- After editing any `.md` here, the `.claude/hooks/refs-postedit.sh` hook runs
  `kusara validate` automatically.
- After editing source under `crates/`, the hook runs `kusara touched` and
  reports which FR is the design of record for the changed file.
- Regenerate indexes with `kusara index`. Audit the graph with
  `/kusara:check`. Sync docs after a batch of changes with `/kusara:sync`.
- The authoritative `refs:` schema lives in `../../.claude/rules/refs.md`.

## Adding a new FR

Copy `_template.md` to `NN-<slug>.md`, fill the frontmatter and sections, then
run `kusara validate` and `kusara index`.
```

## FR authoring tasks (5–15)

Tasks 5–15 each create one FR doc. They share this procedure:

1. Read the cited spec sections in
   `docs/superpowers/specs/2026-05-21-mcp-bus-design.md`.
2. Create `docs/fr/NN-<slug>.md` with the exact frontmatter given in the task.
3. Fill the body sections from `_template.md`, extracting prose from the cited
   spec sections:
   - **Purpose** — the contract / why, from the spec's component intro.
   - **User-visible Behavior** — observable semantics and surfaces.
   - **Capabilities** — bullet guarantees.
   - **Boundaries** — non-responsibilities; pull relevant items from spec §1.1
     (non-goals), §12 (open questions), §13 (future work).
   - **Error Handling** — the spec §8.x cases listed in the task.
   - **Traceability** — the `related` / reference links from the frontmatter.
   - **When to update** — concrete triggers (e.g. "envelope field added or
     renamed", "a new MCP tool is added").
4. Run `kusara validate` — expect no dangling refs (forward references to
   not-yet-written FRs will fail until Task 15; see each task's expected
   output).
5. Commit.

Write prose tight and factual — audiflow style. Do not invent behavior beyond
the spec. If a spec detail is ambiguous, prefer the narrower reading and note
it in Boundaries.
